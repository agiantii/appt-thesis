    幻灯片表存储每个幻灯片文档的标题、内容与状态信息。\texttt{slides}表通过\texttt{parent\_id}字段自关联，这样，空间内的文档就可以支持任意深度的树形结构，如表\ref{tab:slides} 所示。

    评论的树形结构通过\textbf{reply\_id}和\textbf{物化路径（path）}实现，
    如表\ref{tab:slide-comments} 所示。

    \begin{table}[htbp]

    % 删除某条评论及其所有回复时同样也只需要一条如\texttt{DELETE FROM slide\_comments WHERE path LIKE '1-5-\%'}的SQL语句，

    \textbf{为何文档树不使用物化路径？}
    本平台支持用户拖拽来改调整目录树的结构，此时，目录树结构可能会经常变动。
    如果引入物化路径，那么我们每次移动一个节点，都需要更新该节点及其所有子孙节点的\texttt{path}字段，这样会大大增加计算复杂度。
    因此，文档树这边只维护\texttt{parent\_id}字段，移动节点的时候只需要修改该记录的父节点引用。
    删除文档节点时则通过递归遍历依次删除子节点。

    \textbf{为何评论树引入物化路径？}
    \texttt{path}字段存储从根节点到当前节点的完整路径字符串，如\texttt{1-5-12}。
    评论一旦发布，它的结构就不会再发生变化。
    当新增一条评论时，只需要把父评论的\texttt{path}加上当前评论的\texttt{id}，就能得到该评论的\texttt{path}。
    我们可以使用如\texttt{SELECT * FROM slide\_comments WHERE path LIKE '1-5-\%'}的SQL查询语句，一次性获取任意评论节点下的所有子孙评论，不需要递归查询；
    删除某条评论及其所有回复时同样也只需要一条如\texttt{DELETE FROM slide\_comments WHERE path LIKE '1-5-\%'}的SQL语句，不需要递归删除。
    % 另外，评论操作中最频繁的两个场景，正好是物化路径比较擅长的：
    % 一个是展开某条评论下的所有回复，这时候只需要执行如\texttt{SELECT * FROM slide\_comments WHERE path LIKE '1-5-\%'}这样一条SQL查询，
    % 就可以一次性把整个子树取出来，不用递归；另一个是删除某条评论以及它下面的所有子孙回复，
    % 同样可以通过类似 \texttt{DELETE FROM slide\_comments WHERE path LIKE '1-5-\%'} 的单条语句搞定，
    % 这样就避免了逐节点递归删除带来的多次数据库往返。物化路径用冗余一个 \texttt{path} 字段作为代价，
    % 把子树查询和删除的复杂度从递归所需的 $O(n)$ 次查询降到了常数次。在评论这种结构固定、子树操作又比较频繁的场景下，这个做法的性价比确实很高。

    本平台用Yjs库所实现的CRDT算法实现实时协作编辑，

    % TODO 文献引用
    \subsubsection{CRDT基本概念}

    % CRDT作为一种无冲突复制数据类型的算法，能够确保在异步网络环境中，多个数据副本之间最终一致，而不需要中央协调器来解决冲突。

    CRDT算法主要包含两种类型，一种是基于操作的CRDT（Op-based CRDT），通过同步操作序列实现一致性，
    另一种是基于状态的CRDT（State-based CRDT），通过同步完整状态或状态差异实现一致性。

    这个算法处理并发的操作时，不会因为操作的顺序而改变最终的结果，以一个通俗的例子，无论是操作“A”+“B”还是“B”+“A”，其结果都是相同的，
    即使发生网络重传之类等意外情况时，我们可能会意外地执行多个相同的操作，最终的结果也不会受到影响\cite{preguicca2018conflict}。
    % 操作的顺序不会影响最终结果，不管操作按什么顺序到达，最终状态都能保持一致。
    % 操作组合的方式也不会影响最终结果，
    % 而且重复执行相同的操作不会改变状态，网络重传或重复消息不会造成数据不一致。

    % 本平台采用Yjs库实现的基于操作的CRDT算法，该算法具有以下特点：
    % \textbf{交换性}：操作的顺序不会影响最终结果，无论操作到达的顺序如何，最终状态都能够保持一致；
    % \textbf{结合性}：操作组合的方式不会影响最终结果；
    % \textbf{幂等性}：重复执行相同的操作不会改变状态，网络重传和重复消息不会造成数据不一致。

    % \subsubsection{Yjs文档模型设计}

    % Yjs采用分层文档模型设计，核心数据结构包括：\textbf{Y.Text}：富文本数据类型，支持字符级别的插入、删除和格式属性设置，用于表示幻灯片内容；\textbf{Y.Array}：有序数组类型，支持元素的插入、删除和移动，用于管理幻灯片页面顺序；\textbf{Y.Map}：键值对类型，支持属性的增删改查，用于存储幻灯片元数据和用户配置。

    \subsubsection{冲突解决机制}

    当多个用户同时编辑同一文档位置时，CRDT算法通过以下机制自动处理冲突：
    \begin{enumerate}
        \item  \textbf{位置标识算法}：使用唯一标识符（ID）标记每个字符位置，而不是传统的位置索引。字符插入时生成新的唯一ID，删除时标记为墓碑状态。
        \item   \textbf{偏序关系定义}：基于操作ID的因果关系定义偏序关系，确保因果一致性。如果操作A在操作B之前发生，且操作B依赖于操作A的结果，则A必须优先于B执行。
        \item  \textbf{合并策略}：当并发操作无因果关系时，采用确定性合并策略。例如，字符插入冲突时，基于操作ID的字典序确定最终位置顺序。
    \end{enumerate}
    % 第一步，\textbf{位置标识算法}：使用唯一标识符（ID）标记每个字符位置，而不是传统的位置索引。字符插入时生成新的唯一ID，删除时标记为墓碑状态。
    % 第二步，\textbf{偏序关系定义}：基于操作ID的因果关系定义偏序关系，确保因果一致性。如果操作A在操作B之前发生，且操作B依赖于操作A的结果，则A必须优先于B执行。
    % 第三步，\textbf{合并策略}：当并发操作无因果关系时，采用确定性合并策略。例如，字符插入冲突时，基于操作ID的字典序确定最终位置顺序。

    以文本编辑为例，假设用户A在位置P插入字符"X"，用户B又在这个位置插入字符"Y"。
    传统方法会产生冲突，
    而CRDT算法通过以下步骤解决：
    \begin{enumerate}
        \item 为"X"生成唯一ID：\texttt{(clientA, timestamp1)}；
        \item 为"Y"生成唯一ID：\texttt{(clientB, timestamp2)}；
        \item 基于ID排序确定最终顺序：若\texttt{clientA < clientB}，则最终文本为"XY"；否则为"YX"。
    \end{enumerate}
    % 第一步，为"X"生成唯一ID：\texttt{(clientA, timestamp1)}；
    % 第二步，为"Y"生成唯一ID：\texttt{(clientB, timestamp2)}；
    % 第三步，基于ID排序确定最终顺序：若\texttt{clientA < clientB}，则最终文本为"XY"；否则为"YX"。
    % 第一步，为"X"生成唯一ID：\texttt{(clientA, timestamp1)}；
    % 第二步，为"Y"生成唯一ID：\texttt{(clientB, timestamp2)}；
    % 第三步，基于ID排序确定最终顺序：若\texttt{clientA < clientB}，则最终文本为"XY"；否则为"YX"。

    \section{小结}\label{sec:design-summary}

    本章主要说明了平台的设计目标、系统架构和核心功能实现，涉及前后端设计、数据库设计等。
    平台采用前后端分离架构，集成基于CRDT的实时协作、RBAC权限控制以及AI辅助功能。
    % 由此完成智能幻灯片协作编辑的核心能力。

    系统设计在用户体验和技术实现之间做了取舍，尽量做到合理的平衡。
    功能完整的同时，降低了非技术用户的学习难度。
    测试结果显示，功能和体验都达到了设计预期。
    平台可以满足技术演讲者对协作幻灯片的制作需求。

    为了让平台功能更完善、用起来更简单，后续工作将继续提升系统性能和使用体验，增强AI辅助能力。
